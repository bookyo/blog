One header line, two clocks. Ship public, max-age=60, s-maxage=600 and a reader's browser keeps its copy for a minute while the CDN keeps its own copy for ten. Yet only one of those numbers shows up in the curl you ran from your laptop, which is why "I set a short TTL" and "the deploy took twenty minutes to appear" tend to be the same sentence.

One header, four caches, two numbers

A single response can pass four caches before it reaches a reader: the browser's HTTP cache, the CDN edge, an origin shield, and any reverse proxy sitting in between. All four read the same line. According to RFC 9111, max-age applies to all of them and s-maxage applies only to the shared ones, so the header above carries two independent lifetimes — 60 seconds for the private copy, 600 seconds for the edge copy, a 10× gap inside a single directive list. A TTL budget analyzer reports both as separate fields (effectiveBrowserTtl and effectiveEdgeTtl), and the edge value falls back to the browser value whenever s-maxage is missing — which is precisely how a team ends up believing it configured a CDN TTL.

s-maxage is not a bigger max-age

The two numbers answer different questions. The browser TTL answers "how quickly must a fix reach a reader who already has a copy?" The edge TTL answers "how often may this POP wake the origin?" At max-age=60 a single client revalidates up to 60 times an hour; at s-maxage=600 one edge location reaches the origin at most six times an hour, no matter how many readers sit behind it. That is the same object with two bills attached. Shortening the wrong one either fails to fix staleness or multiplies origin traffic for a gain nobody can see.

The shared-cache reading is stricter in a second way. RFC 9111 says s-maxage "also implies the semantics of the proxy-revalidate response directive", so a shared cache may not hand out a stale copy without asking the origin first. A browser may. That asymmetry is the reason a purge feels instant for one user and invisible for the rest of the audience.

The stale window is a budget, not a switch

stale-while-revalidate=30 lets the edge serve a 60-second-old copy for 30 more seconds while it fetches a fresh one in the background. It buys latency, not correctness. stale-if-error=120 applies only when the origin fails; it buys availability, not speed. Stack both on the header above and the worst-case age a reader can see becomes 60 + 30 + 120 = 210 seconds, or three and a half minutes of visible staleness. For example, a price correction written at 09:00 can still be served at 09:03:30 by a cache that never called the origin once during those 210 seconds. That composite figure, not max-age, is what you weigh against how fast a wrong number has to disappear.

Four contradictions the parser never rejects

None of the classic contradictions are syntax errors, so the response ships and the caches disagree in silence:

- no-store beside max-age or s-maxage: both parse, and storage is supposed to lose. - private with s-maxage: one directive confines the copy to the reader, the other targets shared caches. - public with private: two contradictory cacheability claims in one line. - must-revalidate with a stale-* directive: reported as a warning, and the winner differs by implementation.

A conflict detector flags all four and still prints a TTL for each side. For an analyzer that is honest behavior; for a reader skimming the report it is a trap, because the numeric field survives the warning that disqualified it. In that case the report is a list of what the header claims, and the resolution belongs to whichever cache answers the next request.

Where the arithmetic stops

Read the order of operations in the analyzer source and one gap opens. For private, max-age=600 it zeroes the browser TTL, but the edge TTL was copied from the browser value before that zeroing, and only no-cache or no-store zero the edge number. The report therefore shows an edge TTL of 600 for a response that shared caches must not store at all. The number describes the header, not your CDN. Treat private plus any TTL as a case for the response headers on the wire.

The same caution applies to must-revalidate beside stale-while-revalidate. Both directives are valid, they address different moments of a response's life, and implementations order them differently. No calculator can settle that for you; only a probe against your own edge can. Two calls answer it: Age on the second response shows which tier served it, and the observed delta shows how much of the declared TTL was real.

What the edge believes

The authoritative answer arrives in the response, not the request. Age counts seconds since the origin generated or validated the copy; when the measured Age climbs past s-maxage, your TTL is not in charge. Two fields carry most of the answer: Age and Cache-Status, the RFC 9211 summary of hit, miss and remaining TTL. Vendor headers fill in the rest — Cloudflare writes cf-cache-status, Fastly writes X-Cache and X-Cache-Hits, and Akamai writes X-Cache as well.

The CDN selector in the optimizer is deliberately modest about this. It prints fixed posture notes per vendor, and the Cloudflare note reads: "Cloudflare may apply an edge TTL configured by Cache Rules/Page Rules that differs from origin Cache-Control." That is the right level of claim. Vendor behavior changes faster than any table, and the only current statement is the header on the wire.

A pair of headers that holds up under a deploy

Split the jobs instead of tuning one number. A hashed asset gets public, max-age=31536000, immutable: a year, keyed on a filename that changes when the bytes change, with revalidation switched off even on reload. An HTML document gets public, max-age=0, s-maxage=60, stale-while-revalidate=30: the browser always revalidates, cheaply, against an edge copy rewritten once a minute, and the worst case is 90 seconds of age.

One line for both kinds of object is how a project ends up with a TTL that is somehow always wrong — too long for the document, too short for the bundle. Two lines force the right number onto each audience: 31536000 seconds for a hashed asset, 60 for a document, 90 visible seconds in the worst case. The second line also cuts origin traffic from one fetch per reader per minute to six per hour. Try the arithmetic on both at the TTL budget optimizer.

The audit that fits in one curl

Fetch the same URL twice, thirty seconds apart, and read the second response:

curl -sI https://example.com/ | grep -iE '^(age|cache-status|cf-cache-status|x-cache)'

An Age that increases between calls means a hit. No Age at all means each request reached the origin, whatever the request header claimed. The probe shows which tier answered, and the delta between the two calls shows how much of your TTL budget is real. The header you send is not the configuration. It is a request addressed to four caches that each keep their own books, and the only one that answers in public is the Age header on the way back. So the next time a deploy takes twenty minutes to appear, do not re-read the line you wrote — read the receipt, and let the number that comes back overrule the number you meant.
