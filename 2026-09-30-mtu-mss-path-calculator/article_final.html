The Overhead Stack and Why Order Matters

The calculator walks the encapsulation stack in physical-to-overlay order. PPPoE on a DSL link consumes 8 bytes (2 PPP + 6 PPPoE session), leaving 1492 effective MTU on a 1500 underlay. Add VXLAN on top and another 50 bytes disappear; add WireGuard inside that and 32 more; the calculator reports the cumulative subtraction at each step rather than a single black-box number. The order matters because some layers assume IP encapsulation and others assume raw Ethernet — the calculator refuses to silently recompute when you reorder the stack, and it flags when the resulting MSS would fall below the conventional 1380 minimum that most kernel TCP stacks auto-clamp to. Engineers running Calico or Cilium CNIs on top of WireGuard overlays usually arrive at the calculator already suspicious that 1452 is too generous; the tool confirms or denies in one pass.

How PMTUD Failure Looks in Production

Path MTU Discovery works when routers along the path send back ICMP "fragmentation needed" packets, and the source TCP stack shrinks its segment size. It fails when an upstream firewall or load balancer silently drops ICMP — the symptom is a connection that opens, sends the first SYN with a 1460-byte MSS, and then hangs on the first large write. The calculator's DF ping payload size is exactly the test for this: if ping -M do -s fails with Message too long but succeeds with , the path is dropping ICMP and your kernel will keep guessing forever. Most teams find this out at 3 AM when a Kubernetes pod restart loop blames the CNI; the calculator lets you prove the path before you rebuild the cluster.

Choosing the MSS Clamp Target

The conventional wisdom — "clamp MSS to 1380" — survives because most overlay stacks converge there, not because 1380 is special. The calculator computes the actual MSS for your stack, then suggests the conservative 40-byte-below clamp value. For a simple VXLAN overlay on a 1500 underlay, the effective MTU is 1450, the IPv4 MSS is 1430, and the clamp is 1390. For a VXLAN-inside-WireGuard stack, the effective MTU drops to 1368, the IPv4 MSS is 1348, and the clamp is 1308. Setting the clamp 10 bytes higher than calculated will cost you one silent retransmit per connection; setting it 50 bytes lower will cost you 3-4% of long-tail throughput on bulk transfers. The calculator makes the trade-off explicit instead of leaving it in the kernel default.

Verifying the Tunnel End-to-End

Once the calculator gives you a number, the verification loop is short. Run the DF ping from the same network namespace as the client application — not from the host's root namespace — so the test path matches the application's path. If the ping succeeds at the calculated payload and the application's TCP connection still hangs, the problem is downstream of MTU and you should look at TCP window scaling or ECN negotiation. If the ping fails, the path is dropping ICMP or has an unexpected encapsulation the calculator didn't see (most often an MPLS label or a second VPN layer between your tunnel and the destination). The calculator outputs an MSS-clamp suggestion that's safe to deploy even in the "we don't know what's on the path" case; the 1308-clamp is conservative enough to survive most multi-overlay stacks without manual intervention.

The One Decision That Trumps All the Others

Across all the encapsulation and clamping decisions, one is decisive: whether your overlay network has IPv6 in the data plane. IPv6 mandates a 1280-byte minimum MTU and uses a 40-byte header (vs IPv4's 20), which means the calculator's IPv6 MSS output is always 20 bytes lower than the IPv4 output for the same encapsulation stack.
